# Independent trace skill

**Status: accepted.** Component-call reconstruction will be delivered as a new `trace-skill` sibling of `eval-skill` and `metric-skill`. Its stable interface is `fault-trace.json`; the existing evaluation and metric skills remain unchanged initially, so ownership, testing, and future integration stay separate. The current delivery is design-only: implementation is explicitly deferred until separately requested.

## Consequences

- `trace-skill` owns event parsing, timestamp/clock handling, correlation, fault-chain slicing, evidence strength, and trace data generation.
- `eval-skill` remains the owner of diagnosis and root-cause confidence; `metric-skill` remains the owner of existing diagnostic reports.
- `trace-skill` publishes `fault-trace.json`, its JSON Schema, contract-conformance fixtures, and the standalone offline renderer as a reference consumer. Integration with the existing HTML report is owned by the dashboard side and must consume the trace schema through an explicit adapter rather than importing parser or correlation internals.
- The first delivery includes both `fault-trace.json` and a standalone `fault-trace.html`; the HTML is a consumer of the JSON contract, not the contract itself.
- When no diagnosis or timestamp is supplied, `trace-skill` discovers fault-anchor candidates using versioned deterministic severity rules and selects the earliest comparable high-severity anomaly by default while allowing another candidate to be selected. Explicit `FATAL`, crash, panic, abort, OOM, reset, uncorrectable exception, and process-termination records qualify directly; a plain `ERROR` qualifies only through a documented code or event rule. Other errors remain observed anomalies. Candidates in unaligned clock domains are ordered only within their own domain; without an explicit anchor, several domain-local earliest candidates produce a `partial` result with anchor-selection ambiguity, and the HTML opens the candidate selector instead of asserting a global earliest event. A user- or `eval-skill`-supplied anchor takes precedence, and neither automatic nor explicit selection labels an event as the root cause.
- For each fault anchor, the core establishes an execution scope from explicit process-group, session, job, rank, stream/task, and other correlation identities. A process or Device outside that identified scope enters the fault timeline only through a `proven` relationship to it. Concurrent or historical records that cannot be assigned remain auditable in the input inventory and excluded-event counts, but do not enter the selected fault view. When several scopes remain possible, the default `partial` view contains only the anchor's own execution subject and its proven relationships; candidate scopes remain visible and may be selected explicitly in the HTML or through the CLI, but the core never chooses among them using proximity or component convention.
- Time proximity and component rules may produce `inferred` relationships when explicit identifiers are unavailable. They must be visually de-emphasized and excluded from the default highlighted fault chain.
- A relationship is `proven` only when a source record explicitly states the interaction or when compatible records match on explicit correlation identity and execution subject. Multiple weak signals such as time proximity, component order, PID, TID, or Device identity may strengthen an inference but cannot promote it to `proven`.
- The default highlighted fault chain is the graph reachable from the selected anchor through `proven` relationships, in both predecessor and successor directions. Time-adjacent but unconnected events remain non-highlighted context. If no proven relationship reaches another event, only the fault anchor is highlighted; inferred context remains available only in the expanded full-trace view.
- Fault-window limits apply only to non-chain context. By default, the viewer retains context from 1 second before through 100 milliseconds after the selected anchor, capped at 20,000 non-chain events. The selected anchor and its complete reachable `proven` chain remain in the artifact even when they fall outside those limits. When ordinary context is reduced to meet the cap, the JSON and HTML report the truncation and the effective bounds; CLI callers may override the pre-anchor window, post-anchor window, and event cap independently.
- Host and Device records remain on separate clock-domain axes when their offset cannot be established reliably. The viewer must label them as unaligned and must not imply cross-domain ordering or concurrency.
- A wall-clock timestamp without an explicit timezone remains in an unknown-zone clock domain and is ordered only relative to compatible records in that domain. The core never substitutes the analysis machine's timezone or assumes `Asia/Shanghai`. A CLI timezone override may assign the source domain explicitly, but the output records the supplied value and that it came from caller configuration rather than log evidence.
- Clock domains may be aligned only from explicit synchronization/conversion evidence or matched cross-domain events with correlation identifiers that allow the offset to be calculated and validated. The result must retain the offset, method, and uncertainty bound.
- A duration-bearing call span is created only when start and end evidence match by correlation identity and execution subject. Otherwise records remain discrete event points; a reported duration may supplement or validate a span only when its documented semantics identify the measured interval.
- `trace-skill` accepts a raw log directory or archive directly and may optionally consume an `eval-skill` diagnosis or an explicitly supplied fault anchor; it does not require the evaluation skill to run first.
- The timeline groups lanes first by Host/Device location and clock domain, then by component and process. Thread, stream, and task identities are expandable details when present; source log files remain provenance and do not become lanes.
- A deterministic core owns log parsing, event normalization, clock-domain classification, call-span matching, `proven` relationships, fault-chain slicing, schema validation, and HTML rendering. The Agent orchestrates the core, incorporates an optional diagnosis when selecting the fault anchor, explains the result, and may add separately labelled `inferred` relationships; it cannot promote those inferences into the deterministic highlighted chain.
- Directory and archive inputs are exposed through a bounded package reader. It follows nested archives to a maximum depth of two so an outer collection can contain an `asys_output_*.tar.gz`, but rejects absolute paths, parent-directory traversal, and symbolic-link targets. Configurable per-entry and cumulative expanded-size limits prevent resource exhaustion. Rejected or over-limit entries remain in the input inventory with a reason, are never followed or extracted, and make the trace `partial` because their evidence was not inspected.
- The standalone HTML uses synchronized overview and detail timelines. The overview preserves the complete proven fault chain and indicates the active viewport; the detail timeline initially focuses on the selected fault anchor and supports microsecond-labelled zooming and panning without changing the underlying time scale.
- The HTML pairs the timelines with a sortable and filterable evidence table. Selecting an event or span in either representation focuses the same entity in the other, so visual concurrency analysis and source-evidence verification remain synchronized.
- The viewer exposes all detected fault-anchor candidates with their timestamp, component, severity, and selection evidence. An explicit caller or `eval-skill` anchor takes precedence over automatic selection; users may switch candidates in the HTML and the timeline plus evidence table refocus on the corresponding deterministic fault-chain slice.
- The primary visualization is a horizontal, true-scale timeline rather than a UML sequence diagram. Host/Device component-process lanes occupy the vertical axis; observed events are points, matched calls are duration bars, and directed connectors show supported interactions so microsecond spacing and concurrency remain visible.
- `fault-trace.html` is a self-contained offline artifact. Its JavaScript, CSS, icons, and trace data are embedded or sourced from vendored local assets during generation; the delivered file performs no external network requests.
- `trace-skill` exposes a deterministic command-line tool, JSON Schema, and offline viewer template. `SKILL.md` instructs the Agent to invoke that tool and interpret its diagnostics; supported inputs include a log directory or archive plus optional output path, explicit fault anchor, `eval-skill` diagnosis, CANN-version override, and redaction configuration.
- CLI exit status describes artifact generation, not fault presence or trace completeness. Exit `0` means a schema-valid `complete` or `partial` JSON/HTML artifact was generated; `2` means invalid arguments, configuration, or unreadable input; `3` means no usable timestamped event or fault anchor exists; and `4` means an internal, schema-validation, or rendering failure. A collected application's or collector's exit status is retained as evidence metadata and is never passed through as the `trace-skill` exit status.
- Known module and process labels are normalized through a versioned component mapping into stable component identities such as AscendCL, GE, Runtime, HCCL, Driver, Device OS, and AI CPU. Each normalized event retains the raw label and mapping rule; unknown labels remain explicit unclassified components instead of being assigned by the Agent.
- Log formats are handled by versioned parser adapters in an explicit registry. Each adapter declares path and content signatures and claims a file only when its detection rules match. The core first attempts to detect the CANN version from package metadata and accepts an explicit version override; when no specialized adapter matches, it falls back to a generic parser. Files that still cannot be parsed remain in the input inventory with their package-relative path, hash, unsupported reason, and unparsed-record count. An unsupported file does not stop other inputs from being processed, and the result reports adapter versions and parse coverage rather than silently claiming completeness.
- An untimestamped line is attached to a timestamped record only when the selected parser's explicit multiline grammar identifies it as that record's continuation. It extends the evidence excerpt but never creates a new event or inherits a timestamp. Untimestamped fragments that cannot be assigned remain as orphan evidence and do not enter the timeline.
- Output evidence contains a package-relative source path, line number or byte offset, source-record hash, and a minimally necessary redacted excerpt. The standalone HTML embeds only redacted excerpts relevant to the displayed trace and never copies complete source logs; the locator allows an authorized user to verify the record in the original package.

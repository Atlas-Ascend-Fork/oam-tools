# Versioned fault-trace contract

**Status: accepted.** `fault-trace.json` is the stable interchange contract between the deterministic trace core, the standalone viewer, and future dashboard adapters. Every artifact declares a `schema_version` and validates against a published JSON Schema.

## Consequences

- Changes within one major schema version may add optional fields but must preserve the meaning and validity of existing fields.
- Removing a field, making an optional field required, or changing field semantics requires a new major schema version.
- The generator version and parser-adapter versions are recorded separately from the schema version because implementation releases do not necessarily change the contract.
- The fault-anchor severity-rule version is recorded separately, and every automatic candidate retains the matched rule and evidence reference. Log level alone is not a root-cause or high-severity assertion.
- When candidates occupy unaligned clock domains, the contract records each domain-local earliest candidate and an anchor-selection ambiguity instead of a fabricated global order. The absence of an automatic single selection does not invalidate an otherwise schema-valid `partial` artifact.
- The standalone HTML and future dashboard integrations consume the schema rather than importing parser internals or relying on undocumented fields.
- Schema validation failure is a generation failure and must not produce an artifact presented as a valid trace.
- Each timestamp preserves its raw source text. Absolute wall-clock microseconds are encoded as a decimal-string `epoch_us` only when the timezone is established; unknown-zone wall-clock values stay in a distinct clock domain without a fabricated epoch. Plotting uses an integer `offset_us` relative to its declared clock-domain origin, with explicit precision metadata. A caller-supplied timezone records its configuration provenance. Floating-point millisecond timestamps are not part of the contract.
- Equal timestamps do not establish order. When no explicit relationship or ordering evidence exists, events remain simultaneous or order-unknown and overlap on the true-scale timeline. Source path, line number, and event ID provide only a deterministic serialization tie-breaker and must not be interpreted as causal order. An explicit proven relationship may express order between equal-timestamp events without inventing a sub-microsecond offset.
- The contract carries an explicit result status and structured completeness diagnostics. A `partial` artifact remains schema-valid but must expose missing source types, unsupported input files and reasons, unaligned clocks, unmatched spans, parser coverage, and other material evidence gaps; consumers must not present it as a complete call trace.
- The input inventory preserves nested archive provenance and records entries rejected for unsafe paths, symbolic links, nesting depth, or expanded-size limits. Such entries are explicit uninspected-evidence gaps rather than silently absent files.
- Untimestamped continuation lines contribute to a timestamped event only when parser grammar establishes the record boundary; they do not receive their own or an inherited timestamp. Unassigned fragments are represented as orphan evidence with source provenance and remain absent from timeline coordinates.
- The contract records the requested and effective fault-window bounds, the non-chain event-count cap, and whether context was truncated. Context truncation does not make a result `partial` by itself when the complete proven fault chain is retained, but it must remain visible to consumers.
- Each selected fault view records its execution-scope identities, the evidence references supporting membership, and counts of parsed events excluded because they belong to another scope or could not be assigned. Timestamp proximity alone cannot establish scope membership. When membership is ambiguous, the contract carries the candidate scopes and their supporting evidence separately from the minimal proven scope so offline HTML and CLI consumers can select one without relabelling it as proven.
- Conflicting correlation identities, execution subjects, or temporal bounds are retained as structured evidence conflicts. They prevent creation of the affected `proven` relationship or span, and neither source priority nor Agent judgment may silently select a winner.
- Each parser produces a strict semantic fingerprint from the clock domain, exact timestamp, event type, component and execution subject, available correlation IDs, and normalized message fields. Source path and line or byte offset are excluded. Compatible records within one input package are represented by one event node with every source retained as an evidence reference only when their fingerprints match exactly and contain enough discriminating information. A field conflict prevents merging and creates an evidence conflict instead; time proximity or message similarity never triggers fuzzy deduplication. Records from different packages or reproduction runs are never deduplicated or correlated.
- Device references preserve separate `logical_device_id` and `physical_device_id` fields and the namespace of every source value. A logical-to-physical mapping becomes proven only when package metadata, `asys`, `npu-smi`, or driver evidence explicitly establishes it; otherwise the viewer keeps the Device lanes separate and reports the mapping gap.
- Default redaction consistently pseudonymizes usernames, host names, IP addresses, user-directory prefixes, and business file paths. Type-specific aliases such as `HOST-001`, `USER-001`, and `PATH-001` are assigned in deterministic scan order, preserve equality only within one input package and its JSON/HTML artifacts, and do not expose original values or establish cross-package identity. Correlation and diagnostic values including Device, process, thread, task, stream, and event identities, error codes, program counters, and necessary memory addresses remain available.

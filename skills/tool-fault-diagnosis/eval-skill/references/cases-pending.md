## PCASE-004：EI0002 Notify Wait 超时定位流程

### 1. 问题现象描述及版本信息

**1.1 问题描述**
训练或推理过程中出现 Notify Wait 超时（错误码 EI0002），通信算子等待 notify 信号超时导致任务挂死。需先判断是否为全量超时，再分别按全量/非全量流程定位。影响范围为通信挂死，所有 rank 超时退出。

**1.2 配套版本信息**

| 信息名称 | 信息内容 |
| --- | --- |
| CANN 版本 | 8.5.0 |
| HDK 版本 | 未明确 |
| 芯片型号 | 多型号适用 |

### 2. 问题分析

再次发生同问题时，维护人员如何确认是同一个问题：

```
[ERROR] RUNTIME(PID,python):YYYY-MM-DD-HH:MM:SS [device_error_proc.cc:1394] ProcessStarsWaitTimeoutErrorInfo:The error from device(chipId:X, dieId:Y), serial number is N, notify wait timeout occurred during task execution, stream_id:XX, sq_id:XX, task_id:XX, notify_id:XX, timeout=60s.
```

### 3. 问题根因
本条为定位流程类，无单一根因。全量超时可能根因：通信算子下发不一致、两卡互等超时、建链超时比执行超时长。非全量超时可能根因：部分卡少下发通信算子、host 慢卡在 host 侧、卡间不同步（编译/加载 ckpt/数据集下载快慢差异、个别卡有额外操作）。

### 4. 解决方案

**临时规避**：增大 `HCCL_EXEC_TIMEOUT` 超时时间，便于诊断或临时缓解卡间不同步。

**长期解决**：
1. 找到首报错，确认首报错为 notify wait timeout
2. 先排查网络问题（网络故障会导致 notify wait 超时）
3. 判断是否全量超时：`grep "notify wait timeout" -rnl | wc -l`，若等于节点数×每节点卡数则为全量超时
4. 全量超时：获取首尾报错时间，比较上步时间差与 `HCCL_EXEC_TIMEOUT`；小于 timeout 则排查所有卡从首报错开始（通信算子下发不一致、两卡互等超时、建链 timeout）；大于 timeout 则增大 `HCCL_EXEC_TIMEOUT`
5. 非全量超时：关注不报超时的卡是否少下发通信算子（分析 atrace 日志）；若未少下发则排查卡间不同步（编译快慢、加载 ckpt 快慢、数据集下载快慢、个别卡额外操作）
6. 参见 PCASE-030（判断是否全量 notify wait timeout）和 PCASE-031（排查等待关系）

### 4. 解决方案

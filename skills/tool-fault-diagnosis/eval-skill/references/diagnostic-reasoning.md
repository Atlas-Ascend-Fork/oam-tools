# 从现有证据定位故障

目标是给出最有依据的故障解释，以及对应的修复和验证方向。能够比较原因时，
应选择优先解释并说明支持理由；尚未确定的实现细节与已经确认的故障机制分别交代。

## 材料与主问题

先读取用户描述、环境及原始材料，盘点日志和压缩包。保留用户报告的观察、定位、
对照和处置结果及其条件，注明哪些来自用户、附件或本次推断。作者的猜测作为候选；
用户材料已报告定位结果时，据此解释相应机制和条件修复，不因缺少同次附件否定该报告。
用户材料与同次原文冲突时列明冲突。不同任务、设备、时间或版本的材料分别归属，
再依据关联证据解释它们的关系。

### 现场线索表

用户描述、附件、环境清单和原始材料是当前故障的一部分证据，不只是日志索引。盘点后先列出以下字段，并在诊断中逐项回连：

| 线索 | 绑定方式 |
| --- | --- |
| 现象和失败阶段 | 与首个失败任务、时间窗和最终传播错误对应 |
| 硬件型号、CANN/Driver/Firmware | 与日志版本、设备号和加载产物核对 |
| 分支、提交、包名、测试脚本 | 与公开源码、补丁日期、构建/运行路径核对 |
| 算子、API、输入格式和复现条件 | 与 task、kernel、shape、参数和约束核对 |
| 问题单、已知修复、版本标签 | 作为上游候选查资料；检查当前版本是否回退或缺修复 |

用户材料写出的 `OOM`、`crash`、分支名或问题单即使没有在日志中逐字出现，也不能直接降级为“标签”。应先将其作为上游假设，与直接机制和版本差异交叉验证；若用户描述或附件明确写“经定位/根因是/已确认/重复问题单/回退后恢复/修复后恢复”，将其记录为 `reported_finding`。`reported_finding` 是用户材料来源的事实层，必须在最终主诊断中先复述原结论、来源、版本/条件和适用边界；它不等同于本次日志或源码已经独立确认。缺少源码、core、精确参数或复现时，只能将 `implementation_root_cause` 标为 `hypothesis/undetermined`，不能删除或改写用户材料已报告结论。只有同一任务和时间窗的明确反证（例如分配成功后的另一类首错）才足以降低该候选，并说明冲突。用户材料与日志冲突时，分别保留两层事实，说明冲突及需要的判别材料。

### 明确约束的语义闭合

设备 `errorStr` 可能已经给出实现无效的对象、操作和边界。只要原文与同一任务绑定，就可以确认
这一级语义机制：

| 原文形态 | 主诊断应明确写出 | 仍需补齐的实现细节 |
| --- | --- | --- |
| `scalar ... internal buffer ... out of bounds` | scalar 对 AI Core 内部 buffer 的访问越界 | buffer 类型、有效范围、索引和源码构造 |
| `scalar ... GM ... exceeds 48 bits` | scalar 形成的 GM 有效地址违反 48 位地址宽度约束 | 实际地址、加法/转换来源和故障指令 |
| `FIXP ... read L0C ... out of bounds` | FIXP 读取 L0C 的源地址或访问跨度越界 | L0C 指针、偏移、布局、步长和指令参数 |
| `LOAD3D ... start ... illegal` | LOAD3D 起始点违反该搬运边界约束 | `mStartPt/kStartPt`、stride、shape 和实参 |

这一级不是把错误串升级为源码行，也不是编造现场数值；它把设备已经报告的约束违反写完整。将
其放在 `direct_mechanism`；`upstream_trigger` 仍需触发条件或依赖关系的证据。没有独立实现证据时，
将源码变量、常量、分支和指令映射保留为 `implementation_root_cause` 的 `hypothesis/undetermined`。因此缺少源码时仍能交付具体机制和针对
该约束的修复方向。

现象字段中的具体错误串、触发条件和对照实验是 `case_signal`，不是背景摘要。把它们逐项写入
证据表，优先在所有日志成员中搜索同一字符串及其底层变体，再按时间、PID/device/rank、
stream/task 和版本绑定。若用户材料说“某模式偶现”“debug 后不复现”或“某故障注入后出现
Oops”，这能改变候选的优先级和验证方向，但不等于已经证明实现根因；若用户材料直接报告具体
端口、算子、版本差异或错误码，应在主诊断中保留该事实，即使后续日志只出现包装错误。

只分析当前已提供材料，不自行补采、修改现场或重跑业务。按问题查阅专项资料、
匹配版本的公开API或源码；相似案例用于形成和比较候选，不代替本例证据。

## 机制与优先根因

1. **绑定失败对象。** 对齐host/PID/rank/device、stream/task/kernel、故障窗口和阶段，
   从最早有因果意义的异常追到最终报错；异步API和等待者可能只是观察点。
2. **解释违反的约束。** 结合内层错误、指令/参数、输入、资源或依赖说明为什么失败。
   单个外层错误码和分类名称还不足以解释机制。
3. **比较原因。** 用现场事实和适用的领域知识比较有依据的候选，说明优先原因如何
   解释关键证据、竞争解释还差什么判别材料。有支持的推断可以作为最可能原因；
   不要求先取得唯一性证明才给出有条件的诊断与修复。
4. **保留证据层次。** 区分直接机制、最可能的上游触发和未确定的实现细节。
   确定程度对应具体结论；缺少core或复测限制相应判断，不抹去已有证据。
   未提供或未见到的记录不等于针对某假设的反证。
5. **核对派生结论。** 地址差、容量、数量、预算和比例使用计算工具，保留原始操作数、
   来源、单位、范围与比较方向；计算正确不证明假设操作数是现场事实。
   只使用同一对象和统计口径的现场值；缺操作数则保留约束，保留原单位和十六进制值。

### 契约与优先诊断

参数错误日志只证明实现拒绝了某个输入，不证明拒绝行为正确。将现场值、当前检查条件、预期接口契约分开核对：接口及版本、参数是否可选、空指针和零元素 Tensor 的语义、支持的 dtype/shape/SoC，以及封装层是否需要转换。若契约允许省略而实现仍作非空校验，优先分析校验或适配缺陷；若契约明确要求非空，则定位调用方输入。没有对应契约时保留责任边界，不能把报错文本自身当作契约依据，断言调用方错误或擅自断言空 Tensor 等同空指针。

用户材料或附件给出的负向测试预期（例如非法参数应返回错误码，而实际 SIGSEGV）也是要解释的行为差异。按复现条件优先诊断空参校验、元数据访问顺序或错误路径的健壮性问题，并给出首个访问前判空、失败后停止使用输出等具体修复。调用栈缺失限制责任函数和发生位置，不抹去该触发条件；调用方忽略返回值等替代解释若没有本例证据，应列为次要待核分支，不能与主要解释等量并列。

主诊断使用“最可能的原因是 <约束如何被破坏>，依据 <现场/报告证据>；待确认的是 <具体实现细节>”。先给针对优先根因的修复，再给区分候选所需的证据。不将“待确认”重复扩展成“尚未诊断”，也不为消除不确定性而编造源码常量。附件的已报告结论与用户材料采用相同的来源标注规则，逐项区分现场直接证据、作者定位、公开实现和本次推断。

### 根因收敛硬门槛

最终结论必须分成三层，不能把它们合并成一句“根因”：

| 层 | 必填内容 | 允许的状态 |
| --- | --- | --- |
| `direct_mechanism` | 同一任务的首错、设备/组件、错误码或原文机制 | `confirmed` 或 `unresolved` |
| `upstream_trigger` | 版本、输入、资源、依赖或用户材料中的问题单如何触发直接机制 | `confirmed`、`hypothesis` 或 `undetermined` |
| `implementation_root_cause` | 具体参数/API字段、非法值或源码构造及其位置 | 只有具备现场字段、源码 `file:line` 或等价实现证据才可 `confirmed` |

没有实现证据时，必须保留 `hypothesis/undetermined`，不得用“检查参数、反汇编、版本统一”这类计划冒充源码级根因，也不得编造现场未出现的数值。常见签名的必核字段如下；字段未见时写明缺口：FIXP/L0C 检查 `mSize/nSize/srcStride/dstStride/ndNum/srcNdStride/unitFlag`；CUBE/tile 检查 tile 尺寸、L0C/FIXP 指针和偏移；GM 高位检查实际地址及其构造；MTE 非对齐检查基址、偏移和元素/字节单位；LOAD3D 检查 `mStartPt/kStartPt`、stride 和边界；DataCopyPad 检查两侧 padding、`blockLen`、blockCount、src/dst stride 及容量。公开契约只能说明约束，不能替代本次参数或源码证据。

`causal_chain` 每一跳都写 `from`、`to`、`evidence_refs`、`counter_evidence` 和 `status`；并列根因逐项列出，传播错误与上游首错分开。`first_error` 必须给出原始文件、1-based 行号或字节范围、完整原文、时间和实体绑定；若 `run_output.log` 存在，优先引用其首个 EZ9999/包装行，再引用嵌套设备首错，不能只用后置 `Task run failed` 代替。

修复建议按 `root_cause_ref -> exact field/value or constraint -> code/API modification -> validation criterion -> existing/plan` 绑定。版本核对、反汇编、扩大内存和泛化边界回归只能作为辅助步骤；根因未闭合时，建议首先写“需补齐的判别证据”，并明确不能声称已验证。

引用完整字段及关键原文，核对任务和来源。代码地址、数据地址、对象编号、计数、
错误位、错误info和返回码各按自己的含义解释；精确结论需要相应字段或实现依据。
型号、版本和实际加载产物不一致时分别保留，不能自动归因为混装。

## 按现场选择细则

| 当前分析涉及 | 需要读取的细则 |
| --- | --- |
| 多窗口、大日志、重复运行或截断 | [日志读取与关联](diagnostic-log-reading.md) |
| args/para base、PC/耗时、ID/数量、零值寄存器、scalar/FIXP、名称线索、C++符号或传感器单位 | [现场字段语义](diagnostic-field-reference.md) |
| AI Core提取器的多值、summary、覆盖、限额或PC计算 | [字段视图](aicore-field-view.md) |
| shape、切分/搬运参数、unroll或缓冲配置变化 | [算子切分与资源约束](operator-boundary-reference.md) |

按当前待解决的问题读取相关部分，随后回到源日志和具体机制。未读取或截断的范围
如实披露，不将前缀、计数扫描或提取器状态称为完整现场理解。

### 大日志与重复运行

先定位失败窗口并覆盖不同异常签名，按任务身份检查传播关系。完整步骤见
[日志读取与关联](diagnostic-log-reading.md)，包括成功/失败块的语义校验和结束读取的条件。

## AI Core 字面字段视图

多字段核对使用eval-skill入口中的只读提取器；核对覆盖、partial和多值后回读原文。
具体输出语义、参数和限额见[字段视图](aicore-field-view.md)。
提取结果是原文视图，不是设备错误位解码或根因判定。

### 构建产物标签

构建日志中的输出目录、测试目标和产物名是现场材料，不是可忽略的路径噪声。先从
`build_error.log` 读取 `Build files have been written to`、`Built target` 及其上下文，
提取稳定的测试标签，再与设备首错、`errorStr`、kernel/hash 和 PC 对齐。标签如
`fixp_*`、`load3d_*`、`mte_*`、`scalar_*`、`l0*_rdwr_conflict` 或
`*_overflow` 可以说明该构建产物有意覆盖的故障类别；当标签与同一任务的设备错误一致时，
可把它作为用户材料/现场报告的上游线索，写出“该产物标签指向的最可能触发是……”。

标签不等价于源码正文：不能仅凭目录名声称某个 `file:line`、寄存器值、参数数值或执行
分支已经确认。若要写 `implementation_root_cause=confirmed`，仍需现场参数、源码/反汇编
或等价实现证据；否则把标签支持的结论写为 `reported_finding` 或 `hypothesis`，并列出
还需补齐的字段。标签与 `errorStr` 不一致时，不强行拼接两者，分别保留并解释冲突。

## 修复与交付

给出优先修复及有依据的替代分支，每条说明成立条件、修改对象或应满足的约束、
具体动作、验证方式及必要的副作用/回退。源码未提供时仍可说明应修正的边界、
地址构造、参数组合、资源使用或依赖关系，不编造变量值、补丁和固定版本。

区分用户报告已执行、附件可核对和本次独立执行。未执行的修复、复现、换件或回归
明确写为计划；读取日志、提取字段和计算表达式只验证对应记录。
验证围绕原失败条件和边界输入，检查首错消失、输出正确以及性能/资源回归。

正文先给分类、阶段、具体机制和优先原因，再列关键日志原文及位置、定界与定位路径、
修复和验证、可信程度与关键缺口。已经确认的机制明确陈述，有依据的候选说明理由。
最终回复包含完整诊断正文；文件链接、HTML和完整性分数作为附属材料。

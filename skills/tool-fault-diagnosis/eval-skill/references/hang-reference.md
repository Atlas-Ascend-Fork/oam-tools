# 进程卡住与通信超时参考

本页提供字段索引和典型机制线索。诊断步骤、证据盘点、全量统计和结论边界统一见
[卡住与通信超时处理流](fault-flows/hang-flow.md)。只分析已有日志、堆栈、配置和验证
记录，不执行进程附加、信号注入、连通性探测或业务复跑。

HIXL/LLM-DataDist 的 endpoint 建链或点对点传输先读
[HIXL 参考](hixl-reference.md)，区分控制响应与底层通道阶段；下文 collective
一致性检查只用于实际的集合通信。

## 日志字段

| 字段或信号 | 解释与核对 |
| --- | --- |
| `EI0002` | 通信操作超时；需具体 Notify Wait 记录才能选择该等待分支，不自动证明网络故障 |
| `EI0006` | Socket 获取失败；只有具体 `wait socket establish timeout` 等信息才判建链超时 |
| `EE9999` | 通用内部错误，须读内嵌详情，不能单码判 Event Wait 超时 |
| `EE1002` | Stream 同步超时；回查流内任务和生产者，不能直接判算子死循环 |
| `HCCL_EXEC_TIMEOUT` | 按版本核对执行预算、单位、作用阶段和实际生效值；跨 rank 报错差不是等待耗时 |
| `ACL_DEVICE_SYNC_TIMEOUT` | 按适用版本核对同步预算和实际调用，不默认与 HCCL 等待起点相同 |
| `HCCL_IF_BASE_PORT` | 拓扑建链监听端口配置线索，需核对实际监听及占用进程 |
| `HCCL_SOCKET_IFNAME` | Host 网卡选择线索，核对实际端点、路由和所需可达性 |
| `notify wait timeout` / `stuck notify num` | 等待线索；按同次通信域/操作和实体去重，不能以行数或文件数代 rank 数 |
| `localRank` / `remoteRank` | 等待端点，还需 group、轮次、stream/task/notify 和 Record 身份 |
| `streamID` / `taskID` | 关联任务，不能作为存活任务数或全局执行顺序 |
| `rankSize` / `rankId` | 当前通信域参与集合与 rank 映射线索，不默认等于全机物理卡集合 |
| `GEfinalize` | 图引擎清理/生命周期线索；按 PID/rank 关联实际退出记录，不能单独证明进程已退出或退出原因 |

错误码含义以现场版本为准；未提供的对端状态、时钟校准或有效配置保持未知。

## 通信下发与等待关联

在已有 plog 中检索 HCCL `run failed, base info`，结合邻近的多行
TaskExceptionHandler 信息核对：

- `streamID`、`taskID`、`tag[]` 和 `AlgType`。
- `group`、`rankSize`、`rankId`。
- `timeStamp`、`deviceId`、`index`、`count`、`reduceType`、`src`、
  `dst`、`dataType`。

先对齐同一通信域、迭代/操作序号及实际参与集合，再比较 collective 类型、
count/dtype、归约类型和调用次序。打印顺序、累计数量或不同轮次的参数差异不能
独自证明同一次 collective 不一致。

部分框架/版本以小张量 AllReduce 实现 barrier；`AllReduce/count=1/int64/sum`
可以作为线索，但普通业务也能产生相同组合，须由框架调用和 group/序号关联确认。
不能把该组合当作所有版本和后端的固定 barrier 签名。

等待图保留操作、事件身份和生效时间区间，沿 Wait 回查对应 Record。单纯 rank
箭头形成 `A->B->A` 不证明死锁：不同轮次、不同 notify 或先后完成的双向同步
也有这种投影。只有仍未完成且无法推进的同一依赖闭环，才能确认互等。

## 典型机制索引

下列编号保留为机制参考，不代表本库拥有对应的原始现场、修复及复跑记录。
相似现象只提供候选，不能视为本次故障已命中已验证案例。

| 编号 | 方向 | 区分所需证据 |
| --- | --- | --- |
| H001 | Notify Wait 互等 | 同一未完成操作的依赖闭环及无法推进的 Record 端 |
| H002 | 参与者未下发所需通信 | 完整阶段覆盖、匹配 group/序号及缺席原因 |
| H003 | 建链组件不配套 | 双方实际加载版本、兼容契约与具体协议失败关联 |
| H004 | 外层 Event Wait 预算先到期 | 对应 Record/Notify 依赖、实际等待、预算及可恢复进展 |
| H005 | 编译/加载造成进入通信延迟 | 阶段和 rank 映射、持续进展、后续进入记录 |
| H006 | 同次 collective 参数/顺序不一致 | group/序号/类型/count/dtype 及各端下发记录 |
| H007 | 拓扑建链端口冲突 | 配置端口、bind 错误、实际占用进程与时间关联 |
| H008 | Host 权重/数据加载停滞 | 匹配 PID 的多次堆栈、进展与 IO/锁依赖 |

### H001：Notify Wait 互等

全量超时及 rank 双向箭头只说明需检查依赖。按处理流的等待图核对每条未完成边、
Record 和生产者。确认不可推进闭环后，修正导致闭环的调用顺序或依赖；单独增加
timeout 不能修复不可满足的等待。首尾报错差小于预算也不确认该机制。

### H002：参与者未下发通信

部分 rank 超时、其他 rank 不报错时，先区分对端缺日志、已退出、Host 阶段延迟
和实际未下发。只有同次操作及完整阶段覆盖支持“缺少下发”。已有 atrace/应用
进展和堆栈可继续区分编译、权重/数据加载及业务路径。修复对应缺席原因，不能
从没有超时直接推出该 rank 健康或少下发。

### H003：建链组件不配套

具体建链超时加版本差异支持兼容性候选，但版本字符串不同不独自证明协议不兼容；
相同也不证明全栈配套。核对双方实际加载库、芯片、组件依赖/兼容范围及具体失败。
不配套被证实后使用配套组件验证，版本证据不替代端点和链路检查。

### H004：Event Wait 与 Notify 预算

先确认是 Event Wait timeout，再关联对应 Record 及其前置工作。配置大小关系不等于
实际到期顺序：还需起点、单位、作用域与生效值。外层确实早于仍可完成的内层工作
到期时，可提出调整预算的未验证缓解；退出、错配或死锁须解决其原因。
单次不复现不自动证明修复已验证，应覆盖原条件和相关回归。

### H005：编译/加载造成延迟

已有记录明确显示某参与者仍在编译或加载，且该操作是其他 rank 当前等待的生产者
时，可优先分析进入时刻差。核对实际进展、后续下发和延迟可恢复性，再决定预热、
缓存、调度或适当预算。未证实少下发不能反推只是慢卡，较低 CPU 也不证明停滞。

### H006：collective 不一致

在同一通信域和序号上，若一端 AllGather、另一端 AllReduce，或 count/dtype/
归约类型不一致，可支持该次通信契约不匹配。继续追踪分支、异常退出或框架调用
为何造成差异，并针对原因修正；不能将不同操作的参数拼成一条冲突证据。

### H007：拓扑建链端口冲突

拓扑超时本身不证明端口占用。已有 bind/占用记录须对应实际 IP、端口、进程和
故障窗口。成立时按适用版本配置可用端口，并核对防火墙、路由和其他 rank 的
一致可达性；网卡或端口调整是有条件建议，不能由相似案例直接确定参数值。

### H008：Host 加载停滞

已有 py-spy 或 gdb 堆栈可定位观测时的权重加载、dataloader、IO 或锁等待。
单次快照不证明长期卡住，也不证明 Device 从未执行。结合多次采样、文件/网络
进展及任务记录，区分正常慢操作与无法推进的依赖，再提出对应优化或修复。

## 修复与验证

普通诊断直接交付机制、关键原文、候选和边界。显式流水线按
[处理流](fault-flows/hang-flow.md#子步骤产物)记录 H1-H4；缺材料不停止已有证据分析。
只有针对性反证才能排除一个候选，未记录或所测范围未见异常均不等于已排除。

延长超时的建议须有实际进展、有效依赖和可恢复延迟证据，并注明生效阶段、单位、
必要影响及未验证状态。验证记录区分失败、未执行、范围不足和原故障消失且回归
通过，不能由记录存在或一次不复现直接宣称解决。

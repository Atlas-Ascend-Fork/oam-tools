# CANN 分层故障报告模板规则

## 模块边界

把本目录作为可独立替换的报告模块。生成 HTML 报告前完整读取本文件，不要只读取 `index.html` 猜测规则。原有成品案例不随模板提交，版式和内容约束以本文件与空白模板为准。

本目录的两个文件必须一起维护：

- `report-template-rules.md`：唯一使用规范和经验约束。
- `index.html`：自包含空白模板、动态入口和中性预览，不含案例事实。

不得增加其他模板、案例报告、截图、样例 JSON 或图例参考。图标必须内嵌在 HTML 中，不增加独立素材目录。构建器和测试属于调用方的实现，不作为额外模板参考。

`index.html` 直接打开时必须显示中性首错时序和完整架构预览，便于检查证据区以及右侧三层图、长条、硬件卡和连线。预览文字、节点和数量都不是诊断事实；正式构建时必须整体替换两个预览块。

空白架构预览只能使用普通 `.node` 和 `.device`，不得带 `.node.error`、`.node.trigger`、`.runtime-return` 或 `.device.source`。预览中的红色只能来自固定的“错误上报/影响”连线，不得让中性占位内容呈现为已证实根因、直接触发点或硬件故障源。

## 设计依据与优先级

版式还原的唯一权威源是完整 Pixso 工程导出的 `index.html` 及其 `FILE_DATA`，不是设计截图。截图只用于实现后的视觉回归，不能据此目测推断或修改尺寸。当前基准画板为：

- 浅色：节点 `248:76871`，画板 `1920 × 2346`。
- 深色：节点 `248:76134`，画板 `1920 × 2346`。

实现和验收按以下优先级处理：Pixso 节点属性与约束 > 本规则记录的设计令牌 > 浏览器计算样式与坐标测量 > 截图回归。设计工程给出的字体、字号、行高、坐标、间距、颜色、圆角和约束必须逐项落实，不能以“近似”“观感相同”或截图难以分辨为由跳过。

当前桌面设计合同如下；除“首错证据区排版”明确记录的自适应例外外，不得擅自改变：

### 字体合同

原工程浅色、深色画板的字号、行高和字重保持一致，字体族按交付环境统一为系统字体优先。模板不得使用单独的 `system-ui`（Windows 会因此落到 Segoe UI）、非设计值 `650`，或在错误元素上套用 `600/700` 冒充设计字重；`letter-spacing` 全部为 `0`，并用 `font-synthesis: none` 禁止浏览器伪造字重。

字体选择由页面启动脚本写入的 `data-platform` 和三组 CSS 变量统一控制，禁止在组件内重新写一套字体列表：

## 调用流程

1. 只读取当前案例的 eval 产物、原始关键日志和可信度结果。多个案例逐案执行，不共享 JSON、节点或结论。
2. 先执行 metric-skill 的 `scripts/build_html_report.py --init <work-dir>`，生成工作用 `index.html` 与 `report-data.json`。
3. 按本文件的语义规则填写 `report-data.json`。未知信息写“未提供”，不得从模板补事实。
4. 用 `--input`、`--data`、`--output` 构建独立 HTML。输入模板和输出报告必须是不同路径。
5. 按末尾验收清单检查，再交付报告。

不要直接编辑共享 `index.html` 填案例，也不要把已生成的报告作为下一份报告的模板。

## 模板与事实分离

- `index.html` 定义空白槽位、视觉结构和中性预览。
- `report-data.json` 是评估报告进入模板的唯一案例语义入口。
- 先从证据确定节点角色和可信度，再选择模板已有样式；禁止先看颜色或严重程度反推根因。

## 内容映射

- `environment`：环境信息严格使用七个固定字段和顺序：模型、vLLM、CANN Runtime、OS、Driver、Firmware、芯片。`芯片` 永远是环境信息的最后一项，任何案例、数据量、设备数量和模板调整都不得改变其位置。只填证据明确出现的环境信息；案例编号、故障时间和执行场景不得占用环境信息栏，未知值写“未提供”。
- `overview.problem`：写成不依赖错误码和内部函数名也能一眼读懂的完整故障概述。优先使用“在什么业务/执行场景中，哪个对象发生什么直接故障，导致什么可见影响”的自然语言句式；必要的算子、组件或错误码作为定位信息嵌入句中，不能用技术字段堆砌代替叙述。只写当前日志能证实的模型、框架、卡数、服务状态和影响，未知事实不得按常见场景补全。
- `overview.scene`：三个摘要标签固定为“运行场景 / 发生问题 / 业务影响”，只能替换对应值，不能缩写、改名或把字段标签交给案例数据控制。运行场景写“谁在什么流程中做什么”，不能只填算子名、函数名、测试名或一串内部标识；`detail` 仅补充算子、stream/task、源码位置等定位信息。
- `overview.incident`：只写日志直接观察到的核心故障现象，避免把未经证明的底层根因写成事实。
- `overview.impact`：写任务、请求、进程、服务或构建层面的可见结果；不能把错误码或下游内部函数名当成业务影响。
- `component_chain`：直接使用当前案例 trace-skill 的版本化摘要。节点只能来自当前包实际观测到的规范组件；箭头只表达正常调用或任务下发方向。`proven` 与 `inferred` 必须保留原证据强度，构建器不得依据组件名称、颜色、数组顺序或架构常识升级关系。缺少合格关系时保留已观测组件并显示证据不足提示，不隐藏面板、不按架构自动补线。
- `timeline`：只收录日志中实际出现的错误首报及其关键上报/传播，不得为凑数量加入普通执行步骤、复现说明、模板实例化背景或推断事件。钟表图标后的 `time` 必须是日志原文中的时间戳；日志未提供时间戳时统一写“时间戳未提供”，严禁填写“顺序 1”“描述 2”“同一错误块”“随后”“崩溃”等排序词或阶段词，也不得推算、继承或编造时间。下一行左栏 `source` 必须填写当条报错的组件、进程、算子或 Device/rank；函数名只能作为组件后的定位补充，不能单独冒充组件。右栏 `message` 必须填写该主体的关键错误信息，不得用抽象阶段标题代替。每条必须填写 `status` 与 `evidence_strength`，事件数量完全按错误证据增减；只有一条错误时就只显示一条，不得填充版面。
- `critical_log`：保留原始关键日志，不为填满版面扩写、重复或改写日志。
- `diagnosis`：沿用 eval 的可信度等级；可提供 `confidence_score`（0-100），报告顶栏显示为“可信度 X%”，后面不拼接等级或其他字符。`confidence_score` 未提供时，构建器可从旧数据 `diagnosis.facts` 中 label 为“可信度”的 value 解析 `X/100`，再生成 `diagnosis.confidence_display`；没有分数时显示“可信度 未提供”。顶栏只显示一个可信度图标，复用 MC2 Pixso 导出的 `可信_white.svg` 中的渐变与主形状，去掉导出文件中的透明占位矩形，统一浅色/深色主题，尺寸保持 24×24；图标与“可信度 X%”文字均加粗显示并向下偏移 5px 与顶栏基线对齐。`INSUFFICIENT` 不得输出根因定论。诊断下四个事实块的标签由模板固定为“首报 / 根因主体 / 源卡证据 / 客户可做”，案例数据只提供对应值，不得通过 `label` 改变语义。
- `evidence_chain`：逐跳写明输入边界、首报、直接触发、传播、结论边界，不能跳步。
- `remedies`：严格沿用带信息 Pixso 画板的四列语义：已有方案、解决主体、具体动作、时效 / 性质。解决主体描述客户与华为之间的责任归属，只允许 `客户方`、`华为方为主`、`华为方` 三种固定表达；不得写“问题现场、模型侧、开发方、测试方、算子团队、编译器团队”等自由角色。`owner_detail` 只补充协作方式或华为内部执行组件，例如“AE 可指导执行”“框架适配开发 / 客户升级验证”“CANN OP 组件开发”，不能另造第四种解决主体。
- `remedies.layer` 与 `remedies.component`：已有方案名称下方严格采用“一个灰色层级标签 + 右侧普通组件名”的结构。`layer` 只能是 `模型层`、`组件层`、`硬件层`，并且它是该行唯一的灰色标签。`component` 必须直接复用当前报告右侧分层图对应长条节点右上角显示的短组件名：组件层取 `catalog_name`（如 `Runtime`、`OP`、`HCCL`、`CCE`），模型/框架层取节点短 `tag` 或明确的框架名（如 `vLLM / torch_npu`），硬件层取 `Device/rank` 名。该字段优先单行显示，剩余宽度不足时允许换到第二行，最多两行且不得溢出本列；建议不超过 30 个字符。不得写“CANN 日志与异常算子现场”“原业务模型与相同输入”等说明句。方案类型、处理对象、取证范围和验证要求应写入方案名称或“具体动作”，不能挤入 `component`。禁止把 `component` 画成第二个灰色方块，也禁止用 `P0/P1`、取证/诊断等优先级或流程词冒充层级。
- `remedies.timing`：主行使用“时效 / 性质”语义。优先沿用原画板表达：`立即 / 临时`、`配套修复`、`长期 / 根修复`、`长期 / 防御`；证据不足、尚未形成修复方案时可写 `立即 / 取证`、`补证后 / 诊断`、`定位后 / 候选修复`、`修复后 / 验证`。除原画板中的固定表达 `配套修复` 外，斜线左侧必须是执行时点或周期，右侧必须是方案性质；不能只写“复现时、补证后、修复后”。`timing_detail` 应说明代价、验证要求或适用边界，例如“吞吐预计下降”“客户应用修复版本并执行回归”“验证前不得标记为根修复”，不能只写“尚未执行、尚未验证”。
- `remedies.timing_detail`：只说明性能代价、版本/回归要求、验证标准或方案边界，例如“不是根修复”“客户应用修复版本并回归”“用于兜底”；不得重复执行状态。
- `notices`：区分已验证修复、临时规避、补采建议、风险和验证计划。
- `architecture`：只选择当前主故障链实际涉及的模型、框架、组件和硬件实体。层名与节点名必须来自当前日志扫描结果，不得把日志模块字段直接当成架构实体。
- 分层图节点的 `tag` / `catalog_name` 必须是组件短名或实体短名，不能复用 `status` 的状态词（如 `observed`、`propagation`、`unknown`）。渲染正文固定为“状态 · 组件/实体短名 · 详情”，任何“已观察 · 已观察”式的重复标签都必须在构建时报错。

## 首错与红色语义

“首错/首报”只表示日志中最早保留的异常打印，不自动等于首因、根因或故障源。

- `first_observed`、`direct_trigger`、`propagation`、`affected`、`observed`、`candidate`、`unknown` 的时序行保持普通色。
- 只有 `root_cause + proven` 或 `fault_source + proven` 的时序事件使用原红色 `.timeline-row.source`。
- 组件长条只有 `root_cause + proven` 才使用 `.node.error`。
- 硬件卡只有 `fault_source + proven` 才使用 `.device.source`。
- 组件直接报错、超时、严重错误、首报卡、等待卡和受影响卡都不能因此标红。
- `direct_trigger + proven` 只使用模板原有橙色 `.node.trigger`，表示触发点，不表示上游根因。

诊断提示框的红色是原模板的告警强调；红色连线是固定图例中的“错误上报/影响”。两者都不能单独证明根因组件或故障卡。

## 分层图视觉合同

严格保持顶层、组件层、硬件层的竖向顺序。顶层按当前日志实际识别结果显示为“模型层”或“框架层”：有明确模型/模型执行流时使用模型层；只识别到框架且没有模型事实时使用框架层并明确模型未提供。`APP` 等日志模块分类不是架构层名称，也不能作为节点名；应继续读取消息正文、源码路径、进程名或扫描结果，填写有证据的模型、框架或具体实体。

标题和设备图标必须直接使用 Pixso 对应节点导出的原始 SVG，不得用相似图标或内联通用图标替代：环境信息使用 `ic_ict_service_group-1.svg`，修复建议使用 `ic_ict_stop_repair-1.svg`，模型层使用 `ic_gts_modelling-1.svg`，组件层使用 `ic_public_management-1.svg`，硬件层使用 `ic_ict_cpu.svg`，Device 卡使用 `容器91336522-4.svg`。三层标题图标固定为 `16 × 16px`。CPU 原始 SVG 是深色画板资源，颜色方向与另外两个分层图标相反，因此 `.hardware-layer-icon` 在浅色主题使用 `invert(1)`，深色主题必须恢复 `filter: none`。

页面只保留浅色和深色两种主题，不得恢复黑白主题按钮、主题变量或脚本分支。打印样式是输出介质适配，不属于页面主题。

## 固定图例与布线

只允许模板原有两种可见图例：

- `调用/任务下发`：使用 `.connector` 或 `.call-wire`。
- `错误上报/影响`：使用 `.connector.error-connector` 或 `.error-wire`。

不得新增、删除、改名、改色或重绘图例，不得为 `candidate`、`identity` 或 `unknown` 创建第三种图例。

- 模型到首个组件的调用使用原中轴直连。
- 灰色调用/任务下发边必须从上游指向下游，整体向下；其他调用/任务下发走左侧或中轴分支。
- 红色错误上报/影响边必须从故障暴露处指向上游消费者，整体向上；错误上报/影响走右侧或独立回流分支。
- 不让调用线和错误线共用同一侧轨道，不改变原箭头、线型和颜色。
- 相邻节点的边转换为模板连接器前，必须核对源、目标和视觉方向；只有与节点几何方向一致的边可被转换。不得因相邻边转换而吞掉红色回流线、反转箭头或把回流画成向下传播。
- 硬件层存在单卡或多卡往返边时，灰色下行与红色上行必须全程分轨：组件端分别使用中心左偏/右偏锚点，硬件端也分别使用中心左偏/右偏锚点，并使用不同高度的横向总线。不能只错开中段横线而让节点附近的竖线重合。
- 硬件层存在多卡并行边时，灰线使用一条主干向各卡分叉，红线使用与灰线错开的主干向上汇聚。各分支连接对应卡片的独立偏移锚点，不得把所有边和标签画在同一坐标。
- 多卡汇聚线路只允许一个关系标签：组件向多卡下发统一显示“多卡任务下发”，多卡向同一组件回传统一显示“多卡错误上报/影响”；`Notify Wait`、`AllReduce`、`ReduceScatter`、rank 数等具体操作和规模写入对应硬件卡正文，不得作为四个并排线路标签重复绘制。
- 组件层与硬件层之间存在多条边时，每条边必须保留独立的 SVG path 和箭头；同一硬件卡的多条边使用分离锚点和通道偏移，禁止因路径或标签碰撞检测删除边。碰撞检测只允许调整标签位置。
- 连线标签必须短且具体，优先写实际接口、任务或 collective 类型，避免只写含糊的“同一任务/同一 collective”。当卡片已表达首报/后续状态时，硬件红色分支可只画线不重复标签。
- 连线、箭头和标签不得穿过或遮挡层标题、层说明、节点正文、设备标题及其他标签。路由空间不足时按顺序处理：去掉重复标签，分组键固定为（源层，图例，label 文本），同时覆盖 `callIntoHardware` 和 `errorFromHardware` 两种方向，同组只绘制一次标签且位置取组内标签 X 坐标 `min/max` 的水平中点；随后按标签实际包围盒对层标题、层说明、节点、设备、说明文字和已放置标签做碰撞检测，并在水平方向最小偏移避让；合并同角色后续设备；增加层间路由间距。不得通过缩小字体或允许重叠解决。
- SVG 坐标必须先通过 `getBoundingClientRect()` 转换为相对架构画布的 `box()` 结果，再读取 `top`、`bottom`、`left`、`right`、`cx`、`cy`；DOM 元素本身没有这些几何属性，禁止直接使用 `sourceLayer.bottom` 或 `targetLayer.bottom`，否则会产生 `NaN` 路径并让硬件层连线消失。

上述分层架构图固定图例与调用链面板的局部证据图例职责不同。调用链只允许：

- `proven 调用`：绿色实线箭头；
- `inferred 调用`：蓝色虚线箭头，并显示“推断”。

调用链不得显示错误上报/影响方向。卡片按 trace-skill 给定顺序排列，每个组件一张；连线端点必须连接卡片边缘。非相邻边从卡片上方独立通道绕行，不得穿过中间卡片；多条边不得合并成无法区分起终点的公共主干。

## 首错证据区排版

沿用完整字体合同：正文和事件为系统 UI 字体 Regular `14px/22px`，时间为系统 UI 字体 Regular `12px/18px`，原始日志为系统等宽字体 Regular `12px/22px`。不要通过缩小字体解决长文本。

桌面端固定保留时序/原始日志双栏，以约 58:42 作为首次渲染的回退比例，但最终比例必须根据当前浏览器中 `.evidence-layout` 的实际可用宽度和两栏内容动态确定。不能把某个画板宽度下测得的比例固化到所有窗口，也不能依赖 `minmax(320px, ...)`、`minmax(260px, ...)` 等固定最小宽度限制比例搜索；这会在 1536px、1440px 等常用窗口宽度下重新产生明显高度差。

动态等高按以下顺序实现：

1. 在桌面双栏状态下清除上一次计算产生的宽度和补偿值，读取当前 `.evidence-layout` 的实际内容宽度并扣除栏间距。
2. 在保证可读性的边界内逐像素遍历左栏宽度，右栏使用剩余宽度；每一档都读取两栏 `getBoundingClientRect().height`，选择自然高度差最小的一档。高度差相同时优先选择最终总高度较小的档位，避免无意义地拉长首错区。
3. 文本换行和行高会造成离散跳变，只调宽度时通常仍会残留数像素高度差。把该残差仅加到较短栏内容末端：时序栏加到最后一条 `.timeline-row` 的底部内边距，日志栏加到 `.log-box` 的底部内边距。不得通过固定栏高、大块空白、滚动条、裁切或增加无关日志实现等高。
4. 页面首次渲染、字体加载完成以及窗口 `resize` 后都必须重新计算。移动端和打印态改为单栏，并清除动态宽度和高度补偿。

默认保留 4–6 个对因果判断有贡献的关键时序里程碑；同阶段重复超时、后续伴随错误和清理退出应合并概括，只有会改变诊断结论的独立事件才可超过 6 条。长时间戳、事件名和说明必须换行但不能逐字竖排、溢出或遮挡。

这里的动态等高双栏是已确认的设计例外：它替代原工程中会造成大块空白的固定 `240:624` 切分，仅修正首错区的内容适配问题；字号、行高、间距、颜色、圆角及其他区域几何仍以 Pixso `FILE_DATA` 为准。

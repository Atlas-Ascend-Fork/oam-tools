> 本文档提供对度量结果进行深度分析的框架、常见问题的归因方法和改进建议模板，是度量报告中"改进建议"章节的核心参考。

## 二、性能分析框架

### 2.1 判断瓶颈类型

**步骤 1：计算算术强度**

$$\text{算术强度} = \frac{\text{FLOPs}}{\text{访存量(Bytes)}}$$

- 算术强度 > 设备 ridge point → **计算瓶颈**
- 算术强度 < 设备 ridge point → **内存带宽瓶颈**

> NPU ridge point ≈ 理论峰值 TFLOPS / 理论 HBM 带宽 ≈ 320 TFLOPS / 2 TB/s = **160 FLOP/Byte**

**步骤 2：查看 profiling 数据**

| 指标 | 低于阈值的判断 | 可能原因 |
|------|-------------|---------|
| AICore 利用率 < 60% | 算力未充分利用 | shape 太小（无法充分流水）、算子未融合 |
| HBM 带宽利用率 < 50% | 访存效率低 | 访存模式不连续、cache 未命中 |
| `aicore_time / end2end_time` < 60% | 调度开销大 | 小算子碎片化、stream 同步频繁 |

### 2.2 常见性能问题与建议

| 问题 | 改进建议 |
|------|---------|
| 矩阵乘 shape 太小，AICore 利用率低 | 合并小 matmul（batched matmul）；使用算子融合 |
| 激活函数单独执行，调度开销多 | 与前后算子融合（GE 算子融合或手动融合） |
| AllReduce 通信占比 > 30% | 使用梯度压缩；overlapping 通信与计算 |
| 图编译耗时长（> 30s） | 开启编译缓存 `export ASCEND_CACHE_GRAPH=1` |
| HBM 带宽利用率低（访存密集型算子）| 优化数据布局（NCHW → NHWC）；增大 tile size |
| 多卡训练中某卡明显慢（木桶效应）| 检查 rank 间数据不均衡；排查慢卡硬件状态 |

## 三、精度分析框架

### 3.1 精度问题分级

| max_diff 范围 | 严重程度 | 处理优先级 |
|-------------|---------|---------|
| > 0.1 | 严重（计算结果不可用） | P0 立即修复 |
| 0.01 ~ 0.1 | 中等（超出允许范围） | P1 本迭代修复 |
| 0.001 ~ 0.01 | 轻微（在容限边界） | P2 监控 |
| < 0.001 | 正常 | 无需处理 |

### 3.2 精度问题排查步骤

```
1. 打印导致最大误差的输入 tensor 值
   → 是否存在极端值（很大或很小）?

2. 用 FP32 重跑算子
   → FP32 结果是否正确?
   → 若不正确 → 算子逻辑 bug（需修代码）
   → 若正确 → 低精度数值问题

3. 分析数值范围
   → 激活值是否超出 FP16 范围（>65504）?
   → 是 → 使用 Loss Scaling 或换 BF16

4. 逐层比对精度
   → 找出精度首次劣化的层
   → 对该层使用高精度计算
```

### 3.3 常见精度问题与建议

| 问题 | 改进建议 |
|------|---------|
| FP16 溢出（inf/nan）| 开启 Loss Scaling；改用 BF16；关键层用 FP32 |
| 量化精度损失过大 | 增加量化校准数据量；使用混合精度量化（敏感层保持高精度） |
| LayerNorm 精度差 | 强制使用 FP32 计算：`nn.LayerNorm().float()` |
| 大矩阵乘累加误差 | 开启高精度矩阵乘：`torch.npu.set_float32_matmul_precision("high")` |
| Softmax 溢出 | 检查 attention mask 是否含 `-inf`，改用数值稳定版实现 |

## 四、稳定性分析框架

### 4.1 稳定性指标

| 指标 | 计算方式 | 达标标准 |
|------|---------|---------|
| P99/P50 比值 | P99 延迟 / P50 延迟 | < 1.5（性能稳定） |
| 标准差/均值 | std / mean | < 5%（低抖动） |
| 精度一致性 | 多次运行 max_diff 的方差 | < 1e-4 |

### 4.2 抖动问题排查

| 现象 | 可能原因 | 解决方案 |
|------|---------|---------|
| 偶尔出现明显慢帧 | GE 图重编译 | 固定编译输入 shape |
| P99 远高于 P50 | HBM 内存碎片化 | 定期重启或增加预分配 |
| 精度随机波动 | 非确定性算子（如 dropout） | 固定随机种子 |

---

## 五、改进建议优先级矩阵

| 优先级 | 判断标准 | 行动 |
|--------|---------|------|
| **P0** | 影响正确性（精度 max_diff > 0.1 或结果 NaN）| 本次迭代必须修复 |
| **P1** | 性能回归 > 10%，或精度超阈值，或 errMsg 质量分 < 50 | 下一次迭代修复 |
| **P2** | 性能有优化空间（AICore 利用率 < 60%），或 errMsg 质量分 50~69 | 排期优化 |
| **P3** | 代码整洁度、文档完善，errMsg 质量分 70~89 可继续提升 | 长期维护 |

## 六、errMsg 质量分析框架

### 6.1 四维评分方法

errMsg 综合质量分（0~100）= 各维度得分加权求和，各维度权重均为 25%：

#### 维度一：识别完整性得分（0~100）

| 评分条件 | 得分 |
|---------|------|
| 成功提取首报错错误码 | +40 |
| 所有错误码均已识别（无遗漏关键 ERROR 行） | +30 |
| 错误级联深度 ≤ 3 | +20 |
| 错误码按时序排列（首报错在前） | +10 |

#### 维度二：文档符合度得分（0~100）

| 评分条件 | 得分 |
|---------|------|
| `documented_rate` ≥ 80% | +50 |
| `documented_rate` ≥ 60% 且 < 80% | +30 |
| `undocumented_codes` 为空或仅含 `E*9***` 内部码 | +30 |
| `description_match` = true | +20 |

#### 维度三：格式规范度得分（0~100）

| 评分条件 | 得分 |
|---------|------|
| `code_format_compliant_rate` = 100% | +30 |
| `has_ascend_error_block` = true（适用 AI Core Error 场景） | +25 |
| `log_line_format_compliant_rate` ≥ 90% | +25 |
| `has_file_line_info_rate` ≥ 80% | +20 |

#### 维度四：问题指导性得分（0~100）

| 评分条件 | 得分 |
|---------|------|
| `has_module_identified` = true | +20 |
| `has_fault_kernel` = true（AI Core Error 场景） | +20 |
| `has_device_stream_task_info` = true（AI Core Error 场景） | +20 |
| `has_root_cause_hint` = true | +20 |
| `actionable_rate` ≥ 80% | +20 |

### 6.2 各维度问题分析与改进方向

#### 识别完整性不足

| 问题现象 | 根因 | 改进建议 |
|---------|------|---------|
| 首报错码未提取 | 异步场景下日志乱序，serial_number 未被识别 | 按 `serial number` 字段排序后取最小值 |
| 错误码遗漏 | 日志级别设置过高（3=ERROR 时 WARNING 不输出） | `export ASCEND_GLOBAL_LOG_LEVEL=1` |
| 级联深度过大（>5） | 根因未主动分析，跟踪了过多次生错误 | 从首报错算子逐层向上分析，不超过 3 级 |

#### 文档符合度不足

| 问题现象 | 根因 | 改进建议 |
|---------|------|---------|
| `documented_rate` < 80% | 错误码较新（9.0 新增）或文档版本落后 | 对照最新社区版文档更新 err-messages.md |
| 存在 `undocumented_codes`（非内部码） | 自定义算子或第三方库错误码未入库 | 在 err-messages.md 中补充自定义算子错误码 |
| 大量 `E*9***` 内部码 | 问题需要华为介入 | 收集完整 plog + msnpureport 数据，提交ISSUE |
| `description_match` = false | 屏幕打印内容与文档描述不一致（可能是版本差异） | 检查 CANN 版本对应的完整文档 |

#### 格式规范度不足

| 问题现象 | 根因 | 改进建议 |
|---------|------|---------|
| 错误码格式非法（如截断 / 额外字符）| 日志解析脚本正则未覆盖所有格式 | 更新 clean.py 正则规则：`[EWI][0-9A-Z][0-9]{4}` |
| 无 `Ascend Error Message` 块 | 日志采集不完整，或容器内无法获取屏幕输出 | 配置 `ASCEND_SLOG_PRINT_TO_STDOUT=1` 重跑 |
| 日志行缺少 `[File:Line]` | 日志级别为 INFO 或更高，调试信息未输出 | `export ASCEND_GLOBAL_LOG_LEVEL=0`（DEBUG）重跑 |
| 时间戳格式异常 | 容器内时区错误，参见 log FAQ | `export TZ=Asia/Shanghai` 设置正确时区 |

#### 问题指导性不足

| 问题现象 | 根因 | 改进建议 |
|---------|------|---------|
| `has_fault_kernel` = false（AI Core Error）| `Ascend Error Message` 块不完整，`fault kernel_name` 行缺失 | 重新收集完整屏幕输出 |
| `has_device_stream_task_info` = false | 日志截断或 rtStreamSynchronize 层未打印详细信息 | 收集 plog 中对应 stream_id 的上下文 |
| `actionable_rate` < 80% | 大量内部错误码（E\*9\*\*\*），无排查方向 | 参见 fault-handling.md 工具章节，使用 asys/msaicerr |
| `matched_case_ids` 为空 | 问题无历史案例，属于新场景 | 分析后将新案例补充进 cases.md |

### 6.3 errMsg 质量与问题可解性关系

```
quality_level 与问题定位效率关系：

EXCELLENT (≥90)  →  通常可直接定位根因，参文档即可解决
GOOD (70~89)     →  可定位至模块，需结合 cases.md 或 fault-handling.md 进一步分析
FAIR (50~69)     →  只能确定问题类型，需补充收集日志后重新评估
POOR (<50)       →  无法从 errMsg 直接定位，必须重跑并改善日志收集条件
```

## 七、诊断可信度分析框架

> errMsg 质量回答"日志够不够用"，诊断可信度回答"结论站不站得住"。
> 两者可以背离：日志质量 EXCELLENT 但只看了单一来源、没排除竞争假设，可信度依然是 LOW。
> 评分由评估 Skill 的 `assess_confidence.py` 产出，阈值见 `baseline-data.md`。

### 7.1 五维得分解读

| 维度 | 得分偏低意味着 | 对结论的影响 |
|------|-------------|------------|
| D1 证据完整性 | 材料本身不全（首报错缺失、版本未确认、时间线断档）| 结论方向可能整体偏移 |
| D2 证据一致性 | 只看了一个来源，或存在未解释的矛盾证据 | 无法排除单一来源的误报和截断 |
| D3 因果链闭合性 | 根因到现象之间有未证实的跳跃 | 关键环节是假设而非事实 |
| D4 复现与验证 | 未复现、修复未验证 | 结论未经实证检验 |
| D5 知识对齐 | 未对齐官方错误码、案例库或源码 | 可能重复踩已知问题或误判新问题 |

### 7.2 常见低可信模式与改进方向

| 模式 | 典型表现 | 改进动作 |
|------|---------|---------|
| **次报错误导** | 拿到的是清理阶段或下游模块的报错，被当成根因 | 按时间戳回溯到首个 ERROR，异步场景从首报错码开始 |
| **日志被轮转截断** | 早期 ERROR 已被覆盖，只剩崩溃后的日志 | 按 plog 采集文档调大 `log_file_num`/`log_file_size` 后重跑 |
| **符号缺失的堆栈** | 栈帧只有地址或 `??`，函数名不可信 | 用独立符号目录解析 debug so，确认 Build ID 匹配 |
| **单一来源结论** | 只依据 plog 一条日志行下结论 | 补充 device log / 堆栈 / profiling / 源码任一路交叉验证 |
| **因果链跳跃** | "内存不足导致算子失败"但没有内存数据支撑 | 补齐中间环节的量化证据（HBM 占用、shape、地址）|
| **未排除竞争假设** | 只给一个根因，未说明为何不是其他原因 | 逐条列出竞争假设及排除依据 |
| **版本未确认** | 未核对 CANN/Driver/Firmware 与二进制是否匹配 | 确认版本后重新做符号与源码映射 |

### 7.3 可信度与处置优先级

```
HIGH (≥85)          →  结论作定论；关键项满足且修复已验证时沉淀到 cases.md
MEDIUM (70~84)      →  写作"最可能原因"，标注待确认项；案例进候选区
LOW (50~69)         →  写作"初步判断"；优先补齐缺失证据后重评，不入库
INSUFFICIENT (<50)  →  不给根因，只给排查方向和补采清单；回到采集环节
```

可信度不足时，改进优先级排在性能和精度优化之前：结论不可靠，后续优化就是在错误方向上投入。
`assess_confidence.py` 输出的 `missing_items` 已按分值排序，直接作为补证清单使用。

### 7.4 案例库沉淀判定

| 判定 | 条件 | 动作 |
|------|------|------|
| **accept** | HIGH + 关键项满足 + 根因已定位 + 修复已验证 | 写入 `cases.md`，成为后续诊断的匹配依据 |
| **pending** | MEDIUM，或 HIGH 但修复未验证 | 写入 `cases-pending.md`，标注待补证据和转正条件 |
| **reject** | < 70，或关键项（首报错已定位/因果链无跳跃）未满足 | 不入库，先补证 |

沉淀前必须完成脱敏（IP、主机名、家目录、凭据）和重复检索（同错误码同根因优先合并）。
错误案例会被后续诊断反复复用并放大，宁可留在候选区。

## 八、分析报告输出模板

```markdown
## 分析结论

### 主要发现
1. **[P0] 精度问题**：<算子名> FP16 运行 max_diff=0.05，超过阈值 0.01
   - 根因：FP16 累加溢出
   - 建议：对该层启用 FP32 计算

2. **[P1] 性能回归**：端到端时间较基线增加 15%
   - 根因：新增了 2 个小 matmul 未触发融合
   - 建议：检查 GE 融合规则，手动触发 op fusion

3. **[P2] AICore 利用率偏低**：平均 48%，低于阈值 60%
   - 根因：输入 shape 较小（256×256），流水填充率不足
   - 建议：增大 batch size 或使用 batched 版本

4. **[P3] errMsg 质量一般（FAIR 62/100）**：
   - 识别完整性 80 — 首报错码已提取（EZ9999）
   - 文档符合度 55 — 3 个错误码在文档中未找到
   - 格式规范度 70 — 日志行缺少文件名+行号信息（rate=65%）
   - 问题指导性 45 — `fault_kernel_name` 缺失，无法精确定位算子
   - 建议：`ASCEND_GLOBAL_LOG_LEVEL=0` 重跑，补全 Ascend Error Message 块

### 诊断可信度

**综合可信度 78/100（MEDIUM）** — 关键项全部满足，但未复现、修复未验证

| 维度 | 得分 | 说明 |
|------|------|------|
| D1 证据完整性 | 20/25 | 首报错原文已定位；符号部分缺失、复现输入未完整记录 |
| D2 证据一致性 | 20/20 | plog + profiling + 源码三方互证 |
| D3 因果链闭合性 | 25/25 | FP16 溢出 → inf 传播 → NaN 每跳有证据 |
| D4 复现与验证 | 3/15 | 未稳定复现，修复未验证 |
| D5 知识对齐 | 10/15 | 匹配 CASE-001；未完全由源码证实 |

- 关键项：全部满足（首报错已定位、因果链无跳跃）
- 结论强度：当前证据下最可能的原因（不作定论）
- 已证实：LayerNorm 中间激活溢出（源码 + profiling 证实）
- 仍属推断：溢出起始 step 的具体触发条件（缺复现数据）
- 待补材料：debug so 完整符号包（+D1）、稳定复现脚本（+D4 6 分）
- 案例库沉淀：PCASE-001（候选区），补齐符号并验证修复后可转正

### 优化路线图

| 阶段 | 目标 | 预期提升 |
|------|------|---------|
| 本迭代（紧急）| 补齐复现与修复验证，把可信度提到 HIGH；修复精度 P0 问题 | 可信度 ≥ 85；max_diff < 0.01 |
| 下一迭代 | 修复性能回归 | 时间回到基线水平 |
| 后续优化 | 提升 AICore 利用率；改善 errMsg 质量至 GOOD；候选案例转正入库 | +15% 性能提升；errMsg 综合质量分 ≥ 70；CASE 入库 |
```

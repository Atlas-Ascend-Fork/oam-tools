# 度量结果分析文档

> 本文档提供对度量结果进行深度分析的框架、常见问题的归因方法和改进建议模板，是度量报告中"改进建议"章节的核心参考。

---

## 一、分析框架概览

```
度量结果
    │
    ├─ 性能问题？ ──► [性能分析框架]
    │                  ├─ 计算瓶颈
    │                  ├─ 内存带宽瓶颈
    │                  └─ 调度/通信开销
    │
    ├─ 精度问题？ ──► [精度分析框架]
    │                  ├─ 数值溢出
    │                  ├─ 量化误差
    │                  └─ 算子精度 bug
    │
    ├─ 稳定性问题？──► [稳定性分析框架]
    │                  ├─ 硬件随机性
    │                  └─ 内存状态差异
    │
    └─ errMsg 质量？──► [errMsg 质量分析框架]
                       ├─ 识别完整性
                       ├─ 文档符合度
                       ├─ 格式规范度
                       └─ 问题指导性
```

## 二、性能分析框架

### 2.1 判断瓶颈类型

**步骤 1：计算算术强度**

$$\text{算术强度} = \frac{\text{FLOPs}}{\text{访存量(Bytes)}}$$

- 算术强度与对应设备/数据类型的ridge point比较，得到理想roofline下的计算或带宽上界，再用profiling检验实际限制。
- 记录访存层级及运算量口径；缓存复用、流水、同步和Host开销可使实际瓶颈偏离理想上界。

> ridge point = 匹配该数据类型/模式的计算峰值 / 对应存储层级带宽。数值需取现场型号与配置，不统一假设160 FLOP/Byte。

**步骤 2：查看 profiling 数据**

| 观测 | 继续核对 | 候选解释 |
|------|-------------|---------|
| AICore利用率低于同条件基线 | 指标定义、采样窗口、计算/访存流水与关键路径 | 小负载、等待、未充分并行等，不能仅据低利用率定因 |
| HBM带宽未达预期 | 实际传输量、cache命中、访问模式与计算占比 | 计算受限时低HBM带宽可能正常 |
| Device时间占端到端比例下降 | Host、传输、同步、通信及重叠关系 | 只能先确认额外时间所在阶段，不直接归因调度 |

### 2.2 常见性能问题与建议

| 问题 | 改进建议 |
|------|---------|
| 矩阵乘 shape 太小，AICore 利用率低 | 合并小 matmul（batched matmul）；使用算子融合 |
| 激活函数单独执行，调度开销多 | 与前后算子融合（GE 算子融合或手动融合） |
| 通信处于关键路径且明显影响目标 | 核对rank负载、拓扑及重叠；压缩等改变数值语义的方案需单独验证 |
| 图编译耗时回归 | 区分首次编译、缓存命中及动态shape；确认现场支持的缓存机制后做对照 |
| 已确认访存路径受限 | 结合实际算子/后端约束测试布局与分块，检查对齐、片上容量及精度影响 |
| 多卡训练中某卡明显慢（木桶效应）| 检查 rank 间数据不均衡；排查慢卡硬件状态 |

## 三、精度分析框架

### 3.1 精度问题分级

先明确参考实现、绝对/相对误差、输入范围、非有限值与业务容限，再按实际影响分级。没有跨算子、dtype和量纲通用的max_diff严重程度表。既定容限用于验收，不能在看到结果后放宽阈值以宣称通过。

### 3.2 精度问题排查步骤

```
1. 打印导致最大误差的输入 tensor 值
   → 是否存在极端值（很大或很小）?

2. 用 FP32 重跑算子
   → FP32 结果是否正确?
   → 若仍异常 → 继续核对输入、参考实现、算法与高精度执行路径
   → 若恢复 → 支持精度模式相关候选，仍需定位实际计算与累加类型

3. 分析数值范围
   → 激活值是否超出 FP16 范围（>65504）?
   → 是 → 核对首次溢出，测试受支持的FP32/BF16计算路径
   → Loss Scaling用于低精度反向梯度，不能修复前向激活溢出

4. 逐层比对精度
   → 找出精度首次劣化的层
   → 对该层使用高精度计算
```

### 3.3 常见精度问题与建议

| 问题 | 改进建议 |
|------|---------|
| 已确认前向FP16范围不足 | 测试关键计算的FP32或受支持的BF16路径；BF16范围更大但尾数精度更低 |
| 已确认低精度梯度下溢 | 按框架支持的AMP/梯度缩放机制验证，分别监测前向与反向非有限值 |
| 量化精度损失过大 | 增加量化校准数据量；使用混合精度量化（敏感层保持高精度） |
| LayerNorm精度差 | 对齐输入、归一化轴、epsilon与实际累加类型，再测试受支持的高精度路径；仅转换参数dtype不能证明全部计算为FP32 |
| 已定位矩阵乘累加误差 | 核对当前NPU后端及算子支持的精度设置，并用实际输出验证其生效；不假设PyTorch同名设置控制所有NPU路径 |
| Softmax出现NaN/Inf | 检查输入非有限值、全掩码行、mask语义与数值稳定性；`-inf`可为合法掩码值，不能一概删除 |

## 四、稳定性分析框架

### 4.1 稳定性指标

| 指标 | 计算方式 | 判断依据 |
|------|---------|---------|
| P99/P50比值 | 同一负载/采样窗口的P99延迟 / P50延迟 | 对应业务SLO与历史分布，记录样本量 |
| 标准差/均值 | std / mean | 同条件基线及业务抖动预算 |
| 精度一致性 | 固定输入条件下多次运行的误差分布 | 算子确定性约定、随机性与任务容限 |

### 4.2 抖动问题排查

| 现象 | 可能原因 | 解决方案 |
|------|---------|---------|
| 偶尔出现明显慢帧 | GE 图重编译 | 固定编译输入 shape |
| P99远高于P50 | 可能有调度、IO、通信、重编译或内存等待 | 用慢样本时间线定位，再针对已证实机制调整 |
| 精度随机波动 | 随机算子、非确定性执行或实际数据差异等 | 核对输入、模式、种子与后端确定性支持，固定种子不保证所有路径确定 |

## 五、改进建议优先级矩阵

| 优先级 | 判断标准 | 行动 |
|--------|---------|------|
| **P0** | 按任务契约造成严重正确性/可用性影响，如非预期NaN | 按业务严重程度安排修复 |
| **P1** | 超出任务既定的性能/精度预算，或关键诊断证据缺失影响处置 | 按影响及任务时限安排修复 |
| **P2** | 同条件分析已定位可改善的性能路径，或日志改进有明确收益 | 按收益、风险与成本排期 |
| **P3** | 代码整洁度、文档完善，errMsg 质量分 70~89 可继续提升 | 长期维护 |

## 六、errMsg 质量分析框架

### 6.1 四维评分方法

errMsg 综合质量分（0~100）= 各维度得分加权求和，各维度权重均为 25%：

#### 维度一：识别完整性得分（0~100）

| 评分条件 | 得分 |
|---------|------|
| 成功提取首报错错误码 | +40 |
| 所有错误码均已识别（无遗漏关键 ERROR 行） | +30 |
| 错误级联深度 ≤ 3 | +20 |
| 错误码按时序排列（首报错在前） | +10 |

#### 维度二：文档符合度得分（0~100）

| 评分条件 | 得分 |
|---------|------|
| `documented_rate` ≥ 80% | +50 |
| `documented_rate` ≥ 60% 且 < 80% | +30 |
| `undocumented_codes` 为空或仅含 `E*9***` 内部码 | +30 |
| `description_match` = true | +20 |

#### 维度三：格式规范度得分（0~100）

| 评分条件 | 得分 |
|---------|------|
| `code_format_compliant_rate` = 100% | +30 |
| `has_ascend_error_block` = true（适用 AI Core Error 场景） | +25 |
| `log_line_format_compliant_rate` ≥ 90% | +25 |
| `has_file_line_info_rate` ≥ 80% | +20 |

#### 维度四：问题指导性得分（0~100）

| 评分条件 | 得分 |
|---------|------|
| `has_module_identified` = true | +20 |
| `has_fault_kernel` = true（AI Core Error 场景） | +20 |
| `has_device_stream_task_info` = true（AI Core Error 场景） | +20 |
| `has_root_cause_hint` = true | +20 |
| `actionable_rate` ≥ 80% | +20 |

### 6.2 各维度问题分析与改进方向

以下是面向后续日志改进的条件性建议，不构成本轮自动补采、切换配置或重跑要求。当前报告继续使用已有材料，逐项说明缺口及其影响。

#### 识别完整性不足

| 问题现象 | 待验证解释 | 改进建议 |
|---------|------|---------|
| 首报错码未提取 | 可能存在异步上报、局部顺序或解析覆盖问题 | 在同一可比较范围内结合 `serial number`、任务标识与局部时序选择首错候选 |
| 错误码遗漏 | 解析覆盖、源日志缺失、过滤或级别配置等 | 先对照原文和扫描覆盖；配置调整只作为明确的后续验证 |
| 级联深度过大（>5） | 可能混入重复传播或未解释的依赖 | 区分触发与传播，按证据向上追踪；在具体缺口处说明边界，不设固定分析深度 |

#### 文档符合度不足

| 问题现象 | 待验证解释 | 改进建议 |
|---------|------|---------|
| `documented_rate` < 80% | 错误码较新（9.0 新增）或文档版本落后 | 对照最新社区版文档更新 err-messages.md |
| 存在 `undocumented_codes`（非内部码） | 自定义算子或第三方库错误码未入库 | 在 err-messages.md 中补充自定义算子错误码 |
| 大量 `E*9***` 内部码 | 问题需要华为介入 | 收集完整 plog + msnpureport 数据，提交ISSUE |
| `description_match` = false | 屏幕打印内容与文档描述不一致（可能是版本差异） | 检查 CANN 版本对应的完整文档 |

#### 格式规范度不足

| 问题现象 | 待验证解释 | 改进建议 |
|---------|------|---------|
| 错误码格式非法（如截断 / 额外字符）| 日志解析脚本正则未覆盖所有格式 | 更新 clean.py 正则规则：`[EWI][0-9A-Z][0-9]{4}` |
| 无 `Ascend Error Message` 块 | 组件/版本未输出该块、屏幕输出未保存或材料覆盖不足等 | 核对实际输出来源及故障类型；说明缺口，不自动更改配置重跑 |
| 日志行缺少 `[File:Line]` | 格式、版本、组件或解析覆盖差异 | 核对对应日志格式与原文，不能由缺字段直接判定日志级别 |
| 时间戳格式异常 | 解析格式不匹配、字段截断或源格式差异等 | 保留原值，分别核对格式、时区和时钟源；没有统一正确时区，不默认修改现场TZ |

#### 问题指导性不足

| 问题现象 | 待验证解释 | 改进建议 |
|---------|------|---------|
| `has_fault_kernel` = false（AI Core Error）| `Ascend Error Message` 块不完整，`fault kernel_name` 行缺失 | 重新收集完整屏幕输出 |
| `has_device_stream_task_info` = false | 日志截断或 rtStreamSynchronize 层未打印详细信息 | 收集 plog 中对应 stream_id 的上下文 |
| `actionable_rate` < 80% | 大量内部错误码（E\*9\*\*\*），无排查方向 | 参见 fault-handling.md 工具章节，使用 asys/msaicerr |
| `matched_case_ids`为空 | 未检索、库不可用或未命中等，按实际状态区分 | 继续分析当前现场；机制示例不是正式案例证据，案例处置遵守入库门槛 |

### 6.3 errMsg 质量与问题可解性关系

```
quality_level 描述 errMsg 本身的可用程度：

EXCELLENT (≥90)  →  信息较完整，仍需原始上下文和因果证据
GOOD (70~89)     →  有可用定位信息，结合现场和参考文档分析
FAIR (50~69)     →  存在明显缺口，说明受限判断并继续已有证据分析
POOR (<50)       →  信息较少，保留可证实事实和具体缺口，不自动重跑
```

日志质量分不决定根因是否可确认，也不封顶其他已有材料支持的结论。

## 七、诊断可信度分析框架

> errMsg 质量回答"日志够不够用"，诊断可信度回答"结论站不站得住"。
> 两者可以背离：日志质量 EXCELLENT 但只看了单一来源、没排除竞争假设，可信度依然是 LOW。
> 评分由评估 Skill 的 `assess_confidence.py` 产出，规则见 [可信度规范](../../eval-skill/references/confidence-assessment.md)。

### 7.1 五维得分解读

| 维度 | 得分偏低意味着 | 对结论的影响 |
|------|-------------|------------|
| D1 证据完整性 | 材料本身不全（首报错缺失、版本未确认、时间线断档）| 结论方向可能整体偏移 |
| D2 证据一致性 | 只看了一个来源，或存在未解释的矛盾证据 | 无法排除单一来源的误报和截断 |
| D3 因果链闭合性 | 根因到现象之间有未证实的跳跃 | 关键环节是假设而非事实 |
| D4 复现与验证 | 未复现、修复未验证 | 结论未经实证检验 |
| D5 知识对齐 | 未对齐官方错误码、案例库或源码 | 可能重复踩已知问题或误判新问题 |

### 7.2 常见低可信模式与改进方向

| 模式 | 典型表现 | 改进动作 |
|------|---------|---------|
| **次报错误导** | 清理阶段或下游报错被当成根因 | 在已关联的任务和局部时序内回溯触发/传播；不直接跨端按时间戳定因 |
| **材料时间覆盖不足** | 早期事件不可见 | 区分轮转、配置与采集范围；交付已有结论及缺口，后续留存配置按版本核对 |
| **符号缺失的堆栈** | 栈帧只有地址或 `??`，函数名不可信 | 用独立符号目录解析 debug so，确认 Build ID 匹配 |
| **单一来源结论** | 只依据 plog 一条日志行下结论 | 补充 device log / 堆栈 / profiling / 源码任一路交叉验证 |
| **因果链跳跃** | "内存不足导致算子失败"但没有内存数据支撑 | 补齐中间环节的量化证据（HBM 占用、shape、地址）|
| **竞争解释未区分** | 多个有依据候选可以解释同一现象 | 给出相关候选、支持/反对证据及区分条件；没有反证的保持未决 |
| **版本未确认** | 未核对 CANN/Driver/Firmware 与二进制是否匹配 | 确认版本后重新做符号与源码映射 |

### 7.3 可信度与结论边界

按 [可信度规范](../../eval-skill/references/confidence-assessment.md) 保留原始分数和等级，每项结论按支持它的证据表述。已确认机制、有依据的上游候选和未决细节分别保留，不因总分升降而互相改写。
`assess_confidence.py` 的 `missing_items` 作为材料缺口索引；逐项说明限制了什么判断，不因缺口自动补采、重跑或停止报告。建议的优先级依据实际故障影响和证据确定程度。

### 7.4 案例库沉淀判定

沿用 [案例沉淀规范](../../eval-skill/references/case-contribution.md) 的 `accept/pending/reject` 判定，不在报告阶段另设门槛或改分。拒绝入库仍交付诊断报告与证据边界。

沉淀前必须完成脱敏（IP、主机名、家目录、凭据）和重复检索（同错误码同根因优先合并）。
错误案例会被后续诊断反复复用并放大，宁可留在候选区。

## 八、分析报告输出模板

仅填写本次实际记录支持的项目，没有对应测量时不编造数字或基线。默认诊断答复不要求本度量模板。

```markdown
## 分析结论

### 主要发现
- 观测：<本次故障/指标、来源、实体及时间范围>
- 影响与优先级：<任务契约或业务影响，说明依据>
- 已确认机制：<与原始证据对应的直接机制及可信程度>
- 上游候选：<支持证据、适用条件、竞争解释及尚缺证据>
- 条件建议：<针对上述机制的动作、影响和验证计划>

### 基线与度量
- 当前测量：<实际统计值、口径及样本数；未测量则说明>
- 基线：<可追溯来源、环境可比性；缺失则不作达标判断>
- 派生计算：<操作数、单位、工具核算与定义>
- 判断：<按既定任务容限/预算；不复用展示示例数字>

### 诊断可信度与验证
- 各项结论：<已证实、候选、未确定及各自依据>
- 实际验证：<已执行的复现/修复/回归及结果；没有则明确未执行>
- 后续验证：<能区分候选的最小步骤及预期观测，不记为已完成>
- 流水线完整性评分：<显式要求时引用真实检查表和脚本原始结果>
- 案例处置：<按真实证据及准入结果，不把机制示例当作正式案例>

### 后续安排
| 动作 | 成立条件与验证方法 | 已知影响与限制 |
|------|--------------------|----------------|
| <针对本次故障的动作> | <具体证据及预期观测> | <实际约束；未经测量不承诺收益> |
```
